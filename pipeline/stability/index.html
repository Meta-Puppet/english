Keeping the GPU from Crashing

When Unity rendering (Direct3D 11) and AI inference (CUDA/TensorRT) shared a GPU, the GPU reset a few seconds after a scene change. This appendix traces the cause and describes the changes that stopped the crashes. It follows Chapters 4 and 5 of the main pipeline article, with terms explained as they come up.

Prologue What actually happened

Preface

On the exhibition laptop (RTX 5070 Laptop), a dialog appeared every time about 6 seconds after loading the scene. Concludes with "This is an unrecoverable error and the editor will close"
Summarized in 3 lines:
what happenedIn the middle of the experience, the GPU became silent for 2 seconds, and Windows determined that the GPU had frozen and reset the GPU. Unity couldn't stand it and crashed.
what was the causeThe “heavy initial processing” of loading the AI ​​model onto the GPU was running right in the middle of the video being drawn. Moreover, the two jobs that requested reading were touching the same GPU without waiting their turn.
how did you fix itAll the heavy processing was done on the intro screen before the participants pressed START, and during the actual event, they only had to "pick up" instead of "make". I decided to use the same key every time I touched the GPU.

In Chapter 4 of this volume, I wrote about how I moved RVM inference from ONNX Runtime's CUDA EP to a direct call to TensorRT. With that, the reasoning itself started to work. However, when I ran the full experience on my exhibition laptop, the screen above appeared again. Direct3D 11[1], Unity's drawing backend, says "The device has been reset" and crashes with the app. It's not an error in reasoning. This message means that the GPU itself has died and Windows has brought it back to life.

This phenomenon is called TDR[2] (Timeout Detection and Recovery). By default, Windows resets the GPU along with the driver if a task sent to the GPU does not respond for 2 seconds. From the perspective of the app that was reset, all textures and buffers it had up to that point will be invalidated, and Unity will terminate this as unrecoverable. Although the dialog says "this occurs when heavy drawing is done," it does not mean that the problem was actually heavy drawing. The cause of the GPU becoming silent for 2 seconds was elsewhere. This supplement is a record of how we chased down the cause of the problem while misunderstanding it, until we finally settled on a “structure that does not cause spikes.”

  1. Direct3D 11 (D3D11). One of the APIs for issuing drawing commands to the GPU on Windows. It is also used as Unity's drawing backend, and the output of the video decoder and the inference results of RVM are exchanged as memory (texture) on the GPU managed by Direct3D 11. Interoperability with CUDA refers to a mechanism that allows this Direct3D 11 side memory to be directly read and written from the CUDA side. In this appendix, "D3D11 timeline" refers to a single line in which Unity's drawing thread loads instructions to the GPU through this API, and the work on the CUDA side also interrupts this line and uses the same GPU.
  2. Timeout Detection and Recovery. This is a mechanism in the Windows display driver infrastructure (WDDM) that if processing sent to the GPU does not complete for a certain period of time (default 2 seconds), it assumes that the GPU has hung and resets the driver. This is a protection mechanism to prevent the screen from becoming stuck, but from the app's perspective, the D3D11 device suddenly goes into a "removed" state and loses all the resources it had on the GPU.
Chapter 01 Wrong Suspect

Mistaking the Cause of the Crash

The symptoms were characteristic. It always crashed right after switching from the tutorial to the main scene, right after the log showed "Native Init() returned status=0", that is, the initialization of pose estimation RTMPose was successful. In the exhibition build, RVM is already running on TensorRT. At this point, only RTMPose was reading the CUDA EP of ONNX Runtime. CUDA EP brings with it a group of DLLs, cuBLAS, a matrix calculation library, and cuDNN, a neural network calculation library, totaling over 1GB. Load it in the middle of the scene, while Unity's drawing thread is loading instructions for each frame onto the same GPU. When the GPU memory (VRAM) runs out, WDDM saves other resources to system memory, and while the save is being done, the rendering presentation (command to send the finished image to the headset) stops. If it exceeds 2 seconds, it becomes TDR. It made sense.

The first thing I did was change the time. RTMPose initialization was made to wait at least 6 seconds after the scene was loaded, and ONNX Runtime's graph optimization level (the strength of optimization that groups and rearranges operations when loading a model; ALL is the maximum) was lowered from ALL to BASIC. This was because just creating a session (an object containing the loaded model and execution environment) was so heavy that it stopped the GPU's instruction sequence. In addition, the start of the experience has been separated from the completion of RTMPose preparation. First-person gameplay relies solely on Quest's hand tracking, so there was no reason to wait for pose estimation. This has reduced the number of crashes, but it hasn't disappeared. The spike position was only moved back for 6 seconds, but the spike itself was still there.

The next thing I did was delete the CUDA EP that I thought was the culprit. Like RVM, I replaced RTMPose with a direct call to TensorRT (directly using the TensorRT SDK from my code without going through ONNX Runtime), and did not include cuBLAS, cuDNN, and onnxruntime_providers_cuda (the DLL for the CUDA EP itself) from the build. The verification script on the exhibition PC side was also made to fail if these DLLs remained in the plugin folder. I thought this solved the problem and tried it three times on the display PC, but it crashed twice.

At this point, I finally found out that loading the DLL was not the culprit. What remained was the cost of “deserialization,” which involves deploying the TensorRT engine from a plan file to the GPU, and the cost of loading the small program (kernel) that runs on the GPU for the first time. Both are "heavy preparations for the first time only" and remain even if ONNX Runtime is deleted. Both do not disappear even if ONNX Runtime is deleted. I also discovered one aggravating factor that I had introduced myself. I kept the settings from when I was using CUDA EP and set the loading method for CUDA modules (a collection of kernels) to EAGER (read all at startup). This was true when cuDNN's exhaustive algorithm search was focused on initial inference, but for TensorRT, NVIDIA itself recommends LAZY[1]. The plan even contains kernel variants that are never called with the actual input size. Loading all of that at the moment of initialization means that you are making things heavier at the exact moment you want to make them lighter. I changed it back to LAZY and explicitly set it in three places with code so that it would not be overwritten by the environment variable.

  1. CUDA_MODULE_LOADING. CUDA is a setting that determines when to load the GPU kernel embedded in an executable file to the GPU, EAGER loads all kernels at initialization, and LAZY loads only the kernel that is called for the first time on the spot. The default for CUDA 11.7 and later is LAZY, but since it can be overwritten with an environment variable, this implementation explicitly sets LAZY from the program side at startup. TensorRT Best Practices also recommends using LAZY to reduce initialization time and peak memory.
Chapter 02 No Spike By Construction

Designing Out the Spikes

There is a limit to the direction of lightening heavy processing. No matter how you do it, deserializing a plan occupies the GPU on the order of hundreds of milliseconds to seconds. Then choose a time to wake up. Until the participant presses START on the intro screen, the GPU is mostly idle just drawing the logo. During this time, create everything you will need later and keep it in a native plugin (DLL). When the scene starts and the footage comes, I take what I've kept instead of recreating it. This is the current structure, with a worker named mppc_vision_prewarm proceeding through four stages behind the intro screen. This is what "GPU vision warm-up n/4" says at the bottom left of the screen.

4 stages of prewarm (during the intro screen, before the video arrives)
1. CUDA runtime and contextcudart (CUDA runtime DLL), CUDA primary context (working environment for using that GPU) on the same adapter (graphics board) as D3D11, nvinfer (TensorRT execution library)
↓
2. RVM engineDeserialization of plan, execution context (work area for one inference), bank of recursion states r1 to r4 (GPU memory for carrying over information from the previous frame to the next)
↓
3. Deserialization of the RTMPose engine and D3D11 preprocessing resourcesplan, SimCC output buffer (memory for the format in which RTMPose outputs joint positions), preprocessing compute shader (a small program that performs resizing and color conversion on the GPU), input buffer and its CUDA interoperability registration
↓
4. Warm up with zero inputActually run both engines once to load the kernel, reset the RVM recursion state and park

The difficult part was that both RVM and RTMPose were designed to know which D3D11 device (the handle of the GPU used by Unity) to use only after Unity handed them the first video texture. Before the video reaches you, you don't know who the other person is in the first place. Therefore, the prewarm is created first by reverse-looking up the device number on the CUDA side from the adapter on which the D3D11 device is installed, and when the actual initialization comes later, it is handed over after confirming that it is "the same device, same plan, and same input size." If even one of the conditions is not met, the product will not be handed over and will be made on the spot as usual. It was a design that was on the safe side, but this “if it doesn't fit, just silently remake it” later became a trap (Chapter 4).

Another thing is that TDR did not stop just by prewarming the engine. This is because the process (cudaGraphicsD3D11RegisterResource) that registers the input memory to be passed to RTMPose (buffer with UAV [1] created on the D3D11 side) so that it can be read from the CUDA side was still running on the GPU that was drawing. This registration is a heavy procedure that only occurs when D3D11 and CUDA shake hands for the first time, and creates the same kind of spike as deserialization. I cut out the construction of preprocessing resources into a function, created and registered them in the third stage of prewarming, and only received them during the initialization of the production.

At the same time, we also changed the loop structure of the experience. Previously, RVM and RTMPose were shut down after each participant and reinitialized with the next participant. This creates a spike opportunity for each participant. Currently, the workers and engines stay resident for the life of the process, and only pause/resume when switching scenes. pause only stops accepting frames and does not touch any resources on the GPU (engine, buffers, CUDA registrations).

After switching to this configuration, we conducted three verification sessions on the exhibition PC, including one session that ran more than 5,000 frames with RVM and pose estimation enabled, with zero exceptions (errors on the C# side), zero CUDA interoperability errors (map/registration failure), and zero TDR.

  1. Unordered Access View. A "window" for compute shaders to read and write to buffers and textures at arbitrary positions in D3D11. RTMPose's preprocessing involves resizing, color converting, and normalizing the decoded NV12 video using a compute shader and writing it to this buffer, and the CUDA side reads the buffer as it is as input for inference.
Chapter 03 D3D11 / CUDA Contention

Coordinating Access Between D3D11 and CUDA

The night I tested Prewarm on my display PC, I discovered another type of problem. The symptoms are: “Sometimes it stops with a clean CUDA interop error, and sometimes it crashes at TDR without leaving a single line of error log.” Timing changes in results are a classic symptom of competition.

The cause was that RTMPose was being initialized in a background thread and was touching the same D3D11 device as Unity's drawing thread without exclusive control. D3D11's device context (window for loading instructions) is not inherently thread-safe (it is not intended to be used by multiple threads at the same time). Unity has exclusive control over this window by enabling ID3D11Multithread[1], but that lock is only protected by the "party that comes to pick it up." This lock was already applied to the ownership transfer (map/unmap, declaration that CUDA will use this memory now and return it after use), which is done every time inference is made. However, device inquiries and resource registration during initialization were not performed. While the drawing thread is presenting, another thread tries to register the resources of the same device without taking the lock. If you're lucky, you'll get an error; if you're unlucky, the driver will stop working with the GPU. The initialization side was also surrounded by the same lock, and the contents of the error were extracted as strings from cudaGetErrorString (a function that converts the CUDA error code into an explanation) and GetDeviceRemovedReason (a function that returns the reason why the D3D11 device disappeared), and the reason was returned to the Unity side in a readable form instead of a number such as "Status -2011".

If you hold it all the way through the inference, the drawing thread's Present will stall for that amount of time, and if it accumulates it will cause a TDR.

What was once called "inconsistency between the driver and CUDA" can actually be divided into two parts. One is the problem of multiple threads touching the same device at the same time, and this is stopped by the above locking arrangement. Another problem is that the versions of the created environment and the used environment are different, and the TensorRT plan file is tied to the built GPU generation (architecture) and driver version. If you bring in a plan created on another PC, it may not work, but it will pretend to work and be slow or unstable. Therefore, the plan will be created using prepare_rvm_tensorrt.ps1 and prepare_rtmpose_tensorrt.ps1 on the exhibition PC, and will not be placed in the repository. As for the build itself, in the TensorRT version, CMake is used to disable ONNX Runtime's CUDA EP and its dependent DLLs from being bundled, and the verification script plays a state in which the old DLLs remain in the plugin folder. “Something that was supposed to be deleted remains and is read in another route” is the kind of confusion that I suspected when I failed 2 out of 3 times in Chapter 1, and I wanted to structurally prevent this from happening.

  1. ID3D11Multithread. An interface for serializing calls when using D3D11's immediate context from multiple threads. Enter the critical section at Enter() and Leave(). Unity enables this to protect its own drawing thread, but when a native plug-in touches the same device, it is not protected unless the plug-in also explicitly enters/leaves. CUDA cudaGraphicsMapResources does not automatically pass this protection, even though it uses D3D11 context internally.
Chapter 04 Post-merge Review

Fixing the Issues Found in Review

After incorporating the changes so far into the main line, the approximately 6,000 line differences were reviewed again. From here on, we'll get into the details of the code, so feel free to skip to Chapter 5. As a general rule, we decided to only make local fixes that require 1 to 4 lines before the exhibition, and to make any design changes, such as state machine integration or file splitting, after the exhibition. This is because tinkering with a working configuration is more dangerous than remaining bugs. List what you found that directly resonates with your experience.

The top item is, frankly, embarrassing. In Chapter 2, I wrote "TDR zero after 5000 frames," but when I verified that, the prewarm on the RVM side was actually in vain. The reason why TDR did not appear was because the lock and LAZY from Chapter 3, and the prewarm on the pose estimation side (coincidentally, both had the same path creation method) were in effect, and the RVM side was still deserializing live. A “remake if it doesn't work” design, which is taken on the safe side, does not show any symptoms even if it fails, so it hides such oversights. The fix is ​​two lines, but it took one human and three AI reviews to find it.

Chapter 05 Operational Guards

Safeguards for Exhibition Operation

After eliminating anything that could be solved with code, I wrote in my runbook what I would do if something still happened on the day. All the information is in a specific line of Player.log.

The first item in particular is the very lesson of Chapter 4. Nothing changes on the screen whether prewarming is working or not. Even if it doesn't work, the experience will begin, and whether or not TDR will occur is a matter of probability. Therefore, determine the “evidence that it is working” in numbers and look at it the morning of the day.

Epilogue Summary

Afterword

Chapter 4 of the main story was about “moving inferences that don't work,” but this supplement is about “preventing inferences that are moving from taking over the GPU.” If I were to explain what I did in one line, I would simply say that I did not lighten heavy processing, but rather reselected the time and place where heavy processing occurs. Complete everything during the intro screen, when no one is looking, and only pick up during the scene. The moment D3D11 and CUDA touch the same device, they always pass the same lock. Create a plan on that PC. Verify the DLL that was supposed to be deleted.

And I couldn't tell if that structure was really working even by looking at the moving screen. Perhaps the most important lesson of this addendum is that “it stopped falling” is not proof that it was “fixed.” If the pre-warm, which had been used in vain with a single path delimiter, had not been determined based on one line of the log, it would have continued to be vain until the day of the exhibition.
